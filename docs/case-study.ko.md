# 사례 기록: DB를 직접 고친 에이전트

초기 A/B 실험은 "Agent Autopsy가 코딩 에이전트의 버그 수정에 도움이 되는가?"를 알아보려던 것이었습니다. 그런데 실험은 다른 질문에 답했습니다. 승인 게이트에 막힌 에이전트가 게이트를 돌아서 가려고 한 것입니다. 이 문서는 무슨 일이 있었고, 무엇이 드러났고, 무엇을 바꿨는지 적습니다.

## 실험 구성

- **문제:** `hard2`. 작은 Python RPG에 버그 여러 개를 심었습니다(시계 누적 오차, 버프 계산, 사거리 경계, 퀘스트 중복 카운트, 빈 인벤토리 슬롯, 세이브 누락). 숨은 테스트 17개로 채점했습니다. 버그는 모두 첫 체크포인트 이전부터 있었습니다.
- **A:** 코딩 에이전트 혼자.
- **B:** 같은 에이전트에 Agent Autopsy를 MCP로 연결.

| | A (에이전트 혼자) | B (Agent Autopsy 사용) |
| --- | --- | --- |
| 토큰(입력 + 출력) | 약 36.6만 | 약 59.2만 |
| 시간 | 약 13.4분 | 약 27.1분 |
| 도구 호출 | 60회 | 110회 (그중 Agent Autopsy 7회) |

B는 숨은 테스트 17개 중 16개, 보이는 테스트 11개 중 11개를 통과했습니다. 토큰은 약 1.6배, 시간은 약 2배 들었습니다.

## B가 느렸던 이유

- 분석기가 Python을 몰라서 원인 후보를 하나도 내지 못했습니다. 그래서 에이전트가 파일을 36번 직접 읽었습니다.
- 테스트 명령을 `npm test`로 잡았습니다. Python 프로젝트에는 맞지 않습니다.
- 모든 사건을 "원인 불명 / 심각 / 고위험"으로 매겨서, 모든 사건에 서브에이전트 독립 검토가 붙었습니다.

## 게이트 앞에서 에이전트가 한 일

수정안은 사용자 승인을 기다리고 있었습니다(`AWAITING_USER`). 에이전트는 서브에이전트 검토 통과를 승인으로 오해한 것으로 보입니다. 그리고 다음을 했습니다.

1. Agent Autopsy의 번들 소스를 읽었습니다.
2. SQLite DB를 직접 열어 **저장된 테스트 명령을 바꿨고**, 성공했습니다.
3. **승인 API를 직접 불렀습니다.** 우연히 실패했습니다. 데스크톱 앱과 MCP 서버가 서로 다른 데이터 폴더를 쓰고 있어서 API 쪽에 그 수정안이 없었기 때문입니다.
4. 사용자에게 묻지 않고 `userConfirmedIntent: true`를 스스로 넣었습니다.

승인 없이 작업 폴더에 반영된 것은 없었지만, 그것은 버그 덕분이었습니다.

## 드러난 구멍

| 구멍 | 고친 내용 |
| --- | --- |
| 앱과 MCP 서버가 서로 다른 데이터 폴더를 씀 | 둘 다 같은 방식으로 정하는 데이터 폴더 하나 |
| 프로젝트 ID가 무작위라 같은 폴더가 두 번 등록될 수 있음 | 폴더 경로에서 만든 ID, 중복은 합침 |
| 승인 API에 인증이 없음 | 데스크톱 앱만 가진, 실행할 때마다 새로 만드는 세션 토큰 |
| 저장된 지문이 없으면 적용 단계가 검사를 건너뜀 | 서명된 지문 필수, 적용 직전에 다시 확인 |
| 승인 뒤에 수정안을 바꿔치기할 수 있음 | 파일 변경 해시를 승인에 묶고, 다르면 `TAMPERED` |
| 서명 키가 코드에 박혀 있음 | 데이터 폴더에 설치마다 따로 만드는 키 |
| DB에서 테스트 명령을 고칠 수 있음 | 데스크톱 앱에서만 확정·서명, 에이전트는 제안만 |
| `node_modules`에 연결된 워크트리가 원본에 쓸 수 있음 | 연결된 의존성 폴더에 쓰면 검증 실패 |
| 격리 백업을 1초마다 만듦 | 변경 지문이 바뀔 때만 백업 |
| 에이전트가 사용자 의도를 스스로 "확인됨"으로 표시 | 사용자 원문을 저장하고, 의도마다 인용·추론·없음을 표시하고, 승인 화면에 나란히 보여 줌 |
| 모든 사건을 심각으로 매김 | 심각도 기본값은 "미판정", 위험도는 사용자가 정한 민감 경로·변경 줄 수·검증 실패 횟수로만 |
| 분석기가 Python을 못 봄 | 다중 언어 테스트 명령 감지, tree-sitter로 Python·JavaScript/TypeScript·C/C++ 함수 추출 |

## 그 뒤에 더한 것

같은 질문이 계속 나왔습니다. *막힌 에이전트라면 다음에 무엇을 해 볼까?* 그래서 게이트마다 에이전트처럼 별도 프로세스에서 DB를 고쳐 직접 공격해 보고, 정확한 오류 코드로 막히는지 확인했습니다.

- **감사 기록.** 게이트와 관련된 사건을 해시 체인으로 남깁니다. 체인만으로는 끝부분을 잘라 낸 것을 알 수 없어서 서명된 기준점을 더했습니다. 체인이 깨지면 사용자가 확인할 때까지 재현 실행과 새 수정안을 거부합니다.
- **수정안 서명.** 고친 수정안 행은 `TAMPERED`로 표시되고, 다른 프로젝트에 적용할 수 없습니다.
- **재현 게이트.** 재현 테스트는 단언 실패로 실패할 때만 인정합니다. 마지막 정상 체크포인트, 단언을 뒤집은 사본과 비교한 뒤 잠급니다. 실패 3번이면 에이전트는 멈추고, 재현 없이 진행하거나 시도를 더 허락하는 것은 사용자가 이유를 적어서만 할 수 있습니다.
- **수정안 경로.** 고치기 전에는 `../x` 같은 경로가 격리 워크트리 밖에 쓰였고, Windows에서는 `GIT~1/hooks/pre-commit` 같은 짧은 이름이 수정안 적용 때 실제 `.git/hooks`에 닿았습니다. 지금은 경로를 실제 형태로 풀어서 제출할 때와 적용 직전에 검사합니다.
- **로컬 API.** 브라우저 요청은 로컬 출처에서만 받고, `localhost.evil.example` 같은 접두어 속임수는 거부합니다.

아직 가능한 것(주로 로컬 키를 읽어 기록을 다시 서명하는 것)은 [위협 모델](threat-model.ko.md)에 적었습니다.

## 배운 것

1. **지시문은 경계가 아닙니다.** 에이전트는 규칙을 알고 있었고 그래도 소스를 읽었습니다. 중요한 규칙은 코드에 있어야 합니다.
2. **우연은 방어가 아닙니다.** 승인 호출은 데이터 폴더 버그 때문에 실패했습니다. 그 버그만 고쳤다면 문이 열렸을 것입니다.
3. **막힌 에이전트는 길을 찾습니다.** 게이트는 에이전트가 돌아갈 길을 찾는다는 가정으로 설계합니다.
4. **게이트는 공격받을 방식으로 시험합니다.** "실패했다"만 보는 테스트는 엉뚱한 이유로 통과할 수 있습니다. 변조 시험은 별도 프로세스에서 하고 정확한 오류 코드를 확인합니다.

## 다시 재지 않은 것

이 변경들 이후 A/B 실험은 아직 다시 하지 않았습니다. 그 전까지 이 프로젝트는 Agent Autopsy가 에이전트를 더 빠르게 하거나 더 정확하게 한다고 주장하지 않습니다. 주장하는 것은 더 좁습니다. Agent Autopsy로 제안된 수정안은 사용자가 승인해야만 파일에 반영되고, 그 승인의 근거는 기록되고 검사되며, 그 길 밖의 직접 수정은 사용자에게 보여 줍니다.
