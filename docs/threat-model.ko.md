# 위협 모델

Agent Autopsy는 코딩 에이전트와 사용자 파일 사이에 있습니다. 이 문서는 무엇을 지키는지, 누구로부터 지키는지, 어떤 장치가 있는지, 그 장치가 어디까지인지를 적습니다.

## 공격자는 누구인가

가장 큰 위협은 **코딩 에이전트 자신**입니다. 에이전트는 사용자 PC에서 사용자와 같은 OS 계정으로 돌고, 다음을 할 수 있습니다.

- 셸 명령 실행, 파일 읽기·쓰기, Agent Autopsy 자체의 소스와 번들 읽기
- 로컬 SQLite 데이터베이스를 직접 열어 아무 행이나 고치기
- `127.0.0.1`의 로컬 HTTP API 호출

예상하는 동기는 악의가 아니라 조급함입니다. 게이트에 막힌 에이전트가 그 게이트를 넘어가려고 합니다. 가정이 아니라 실제로 있었던 일입니다. 초기 A/B 실험에서 에이전트가 바로 그렇게 했습니다([사례 기록](case-study.ko.md)).

범위 밖: 관리자 권한을 가진 악성 프로그램, 네트워크 공격자(API는 `127.0.0.1`에서만 열림), 읽지 않고 승인하는 사용자.

## 설계 목표

> **에이전트가 서명 키 없이 할 수 있는 조작은 막거나 사용자에게 드러낸다.**
> 키를 가지고 기록을 위조하는 것은 문서에 적은 한계이며, 막는다고 주장하지 않는다.

설치마다 서명 키를 따로 만듭니다(데이터 폴더의 `.auth_secret`). 승인, 수정안, 테스트 명령, 잠긴 재현 테스트, 감사 기록이 이 키로 서명됩니다(HMAC-SHA256). 새 우회 방법이 나오면 먼저 *키 없이 가능한가?* 를 묻습니다. 가능하면 고치고, 불가능하면 여기에 적습니다.

## 장치

| 에이전트가 시도할 수 있는 것 | 결과 | 위치 |
| --- | --- | --- |
| 승인 API를 직접 호출 | 거부(401). 승인에는 실행할 때마다 새로 만드는 세션 토큰이 필요하고, 이 토큰은 데스크톱 앱만 가지며 디스크에 쓰지 않습니다. | `api-server.ts`, `electron/main.cjs` |
| DB에서 테스트 명령 고치기 | 테스트 명령은 사용자가 앱에서 확정할 때 서명됩니다. 바뀌었거나 서명이 없는 명령은 실행하지 않습니다(`BLOCKED_TEST_COMMAND_UNCONFIRMED`). | `incident.ts`, `project.ts` |
| 승인 뒤에 수정안 바꿔치기 | 승인에는 실제 파일 변경의 서명된 지문이 붙고, 적용 직전에 다시 확인합니다. 다르면 `TAMPERED`로 표시합니다. | `repair.ts` |
| 저장된 수정안 행 고치기 | 수정안 행마다 서명이 있습니다. 고친 행은 `TAMPERED`, 서명 없는 행(`LEGACY_UNSIGNED`)은 승인할 수 없습니다. 다른 프로젝트의 수정안은 거부합니다(`PROJECT_MISMATCH`). | `repair.ts`, `database.ts` |
| 수정안으로 저장소 밖에 쓰기 | 제출할 때와 적용 직전에 경로를 검사합니다. 절대 경로, `..`, `.git`, 드라이브·스트림 콜론, 정션, 심볼릭 링크, Windows 짧은 이름(`GIT~1`)을 거부합니다(`INVALID_FILE_PATH`). | `utils/paths.ts` |
| "검증" 중에 원본 건드리기 | 모든 수정안은 먼저 별도 git 워크트리에서 돕니다. 실행 중 연결된 의존성 폴더에 쓰면 검증이 실패합니다. | `worktree-runner.ts` |
| 재현 테스트를 고쳐서 수정안 통과시키기 | 재현된 테스트는 서명된 해시로 잠깁니다. 그 테스트를 고치는 수정안은 거부(`REPAIR_MODIFIES_LOCKED_TEST`), 디스크에서 바뀌어도 거부(`LOCKED_TEST_MODIFIED`), 잠금을 지우면 감사 기록으로 드러납니다(`LOCK_REMOVED`). | `repair.ts`, `reproduction.ts` |
| 재현 안 되는 테스트로 계속 재시도 | 실패 3번이면 사건이 기권 상태가 됩니다. 이 게이트는 상태 열이 아니라 감사 기록으로 계산하므로, 저장된 상태를 고쳐도 풀리지 않습니다. | `reproduction.ts` |
| 재현 생략이나 추가 시도를 스스로 결정 | 데스크톱 앱의 버튼(토큰 필요)으로만 할 수 있고, MCP 도구에는 없습니다. 결정마다 이유를 적어야 합니다. | `api-server.ts`, `DecisionModal.tsx` |
| 감사 기록 고치기·지우기·순서 바꾸기·끝부분 잘라 내기 | 기록은 HMAC 해시 체인이고, 서명된 기준점(`audit_head.json`)이 마지막 기록을 기억하므로 끝부분 잘라 내기도 잡힙니다. 체인이 깨지면 사용자가 앱에서 확인할 때까지 재현 실행과 새 수정안을 거부하고, 깨지기 전에 등록된 사건은 다시 결정해야 합니다. | `database.ts` |
| 사용자가 적은 결정 이유 고치기 | 이유는 해당 감사 기록 옆에 저장하고 그 기록의 해시와 대조합니다. 정상, 불일치, 기록 없음, 검증 안 됨(그 앞에서 감사 기록이 손상된 경우)으로 보여 줍니다. | `database.ts` |
| 수정안을 내지 않고 작업 폴더를 직접 고치기 | 막지는 않습니다. 마지막 체크포인트 이후 바뀐 내용을 찾아 "미승인 직접 수정"으로 보여 줍니다. | `project.ts`, `IncidentAnalysisView.tsx` |
| 웹 페이지에서 API 호출 | API는 `127.0.0.1`에서만 열립니다. 브라우저 요청은 로컬 출처(`127.0.0.1`, `localhost`, `[::1]`, 앱 자신)여야 합니다. | `api-server.ts` |

대부분의 경우에 `packages/core/test`에 테스트가 있습니다. 에이전트처럼 **별도 프로세스**에서 DB를 고친 뒤, 그냥 실패했는지가 아니라 정확한 오류 코드로 실패했는지 확인합니다.

## 알려진 한계

고치지 않고 받아들인 것들입니다.

- **서명 키를 읽을 수 있습니다.** 같은 OS 계정의 에이전트는 `.auth_secret`을 읽어 수정안, 잠금, 감사 기록 체인 전체, 기준점까지 다시 서명할 수 있습니다. 그러면 위 장치들은 그 변경을 알아채지 못합니다.
- **한꺼번에 지우기.** 감사 기록 전체와 기준점을 함께 지우면 새로 설치한 것과 구분되지 않습니다.
- **세션 토큰은 메모리에 있습니다.** 데스크톱 앱이 가지고 있다가 실행할 때 백엔드 프로세스에 넘깁니다. 같은 계정의 다른 프로세스는 원리상 프로세스 메모리나 환경 변수를 읽을 수 있습니다. 실제로 시험하지는 않았습니다.
- **토큰이 필요 없는 API가 있습니다.** 재현 실행, 개요 조회, 에이전트 이벤트 기록, 서브에이전트 검토 제출, 이미 승인한 수정안 적용은 아무 로컬 프로세스나 부를 수 있습니다. 이 중 어느 것으로도 수정안 승인, 테스트 명령 확정, 재현 결정은 할 수 없습니다.
- **신고 원문은 지어낼 수 있습니다.** 사용자 원문(`userReportText`)은 에이전트가 넘깁니다. 승인 화면에 원문과 에이전트의 해석을 나란히 보여 주지만, 정말 자기 말인지 확인하는 것은 사용자 몫입니다.
- **서명 없는 표.** 체크포인트, 에이전트 이벤트, 지시(directives)는 서명하지 않으므로 직접 쓰기를 알아채지 못합니다.
- **샌드박스가 아닙니다.** 에이전트의 셸을 제한하지 않습니다. 직접 수정은 보여 줄 뿐 막지 않습니다.
- **잘못된 경보.** 의존성 폴더 감시는 다른 프로그램의 쓰기(예: 실행 중에 사용자가 한 `npm install`)도 잡습니다.
- **플랫폼.** 경로 검사와 변조 시험은 Windows에서 돌렸습니다. Linux에서는 정상 파일 이름이라도 `:`가 들어 있으면 거부합니다.
